# Известные ограничения и следующие инженерные задачи

Этот список описывает текущий код, а не новые реализованные возможности.
Порядок учитывает цель: личный помощник на нескольких устройствах. Для каждого
пункта указан практический критерий завершения, чтобы следующий разработчик мог
продолжить работу без повторного архитектурного исследования.

## Исполнение и восстановление

| Область | Текущее ограничение и последствие | Критерий исправления |
|---|---|---|
| Повтор HTTP-запроса | `run_id` группирует журнал, повтор `/tools/call` исполняется снова | Устойчивый call ID, ключ идемпотентности, сохранённый результат и тест повторной доставки |
| Неопределённый эффект | При 5xx/обрыве gateway останавливается, но не знает фактического результата | Статусы исполнения, сверка с интеграцией и явное пользовательское продолжение |
| Подтверждение после рестарта | Future утрачен, pending action может остаться; старый kind approval не восстанавливает функцию | Durable approval с версией/сроком/состоянием операции; stale-запись не возобновляет эффект |
| Журнал инструментов | Только имя/статус, нет времени и ID отдельного вызова; нет ротации | Структурированные метаданные, политика хранения, корреляция без содержимого секретов |
| Сохранение ответа ИИ | Ответ, факты, задачи и actions применяются последовательно без общей транзакции | Валидированная команда и определённая транзакционная граница; проверка сбоя между шагами |
| Локальная валидация ИИ | Финальный JSON не полностью проверяется по схеме; условные поля операций не выражены | Типизированные операции с проверкой обязательных полей до изменения БД |
| Равенство провайдеров | Общие tools есть, встроенные web/image-функции Claude не перенесены | Явные capability flags; честный интерфейс возможностей каждой модели |

До появления устойчивых run/call-состояний сохранять консервативный запрет fallback
после dispatch. Разрешение автоматического retry только потому, что операция
«обычно быстрая», разрушит уже реализованную защиту от дубликатов.

## API и несколько устройств

| Область | Ограничение | Критерий исправления |
|---|---|---|
| Транспорт | Bind только localhost; нет удалённого подключения | Приватный транспорт с аутентификацией конкретного устройства и отзывом доступа |
| Права | Один bearer даёт все возможности, включая approval | Права по устройству/возможности, явный канал принятия решений владельцем |
| Контракт | Нет версии API, схем всех запросов и единой ошибки | Версия, машинный код ошибки, contract tests и совместимость клиента |
| Валидация legacy API | `bool('false')` даёт true; due/title приводятся непоследовательно | Строгие request models; некорректные типы получают 400 до эффекта |
| Длинный запрос | UI ждёт 330 секунд, approval — 600 | Chat run ID, асинхронное получение результата/прогресса, явная отмена |
| SSE | Очередь 200, drop новых событий, нет replay | Сохранённые sequence IDs, восстановление после reconnect или согласованный snapshot-протокол |
| Напоминания | sent до доставки; Telegram-ошибки без retry | Outbox/очередь доставки, подтверждения/повторы и отдельные статусы для каналов |
| Фоновые команды API | `started:true` без job ID; create_task теряется при рестарте | Устойчивые jobs, состояние/ошибка/отмена через API |
| История | `/state` возвращает 60 сообщений и текущий лист | Отдельные пагинированные endpoint истории и явная семантика snapshot |

API нельзя делать публичным простой заменой IP. Даже приватная сеть не заменяет
идемпотентность, отзыв токена потерянного телефона и восстановление событий.
Сначала сохранить один основной узел с БД, затем подключать клиентов и исполнителей
устройств к определённым контрактам. Копирование живой SQLite между устройствами
не является протоколом синхронизации.

## Данные и фоновая работа

| Область | Ограничение | Критерий исправления |
|---|---|---|
| Analysis worker | Нет running/lease/атомарного claim | Захват задания, recovery зависшего worker, тест двух конкурирующих исполнителей |
| Вход job | Digest заново собирается из изменяемых events | Неизменяемый snapshot или версия/хеш входных границ |
| Повтор анализа | Память может примениться до сохранения done | Идемпотентное применение результатов, происхождение каждого изменения |
| Ссылки SQLite | REFERENCES объявлены, foreign_keys не включён | Аудит существующих ссылок, миграция и включение enforcement |
| Время | Локальные naive строки, нет единого UTC-контракта | UTC событий, timezone пользовательских сроков, миграция и тесты границ суток |
| Удаление/исправление источника | `INSERT OR IGNORE` оставляет первую версию события | Политика версий, изменения/удаления и пересчёта производной памяти |
| Очистка полей | COALESCE смешивает «не менять» и «очистить» | Patch-модель с отличием отсутствующего поля от null |
| Объём истории | Нет общего срока хранения raw/events | Настраиваемое хранение, архивирование и понятное удаление по запросу владельца |
| Privacy helper | Фильтр ключевых слов не обезличивает контекст/URL | Явные правила передачи по источникам и категориям, проверяемые примеры |
| Бюджет ИИ | Оценка по таблице цен, нет резерва in-flight/периодов | Учёт фактического usage, резервирование и отдельный период бюджета |

## Конфигурация, хранилища и эксплуатация

- **Первичная установка:** `_wait_for_data` ждёт уже существующий `db` до load.
  Исправление должно различать новый каталог и недоступный том, не создавая
  случайно новую пустую рабочую БД вместо отключённого хранилища.
- **Переносимость:** сенсоры сеанса рассчитаны на KDE Plasma (KWin-скрипт, `qdbus6`,
  Spectacle); на GNOME и других окружениях активное окно и снимки экрана не работают.
  Корни источников задаются `PERSONAL_DIRS`/`UBERMENSCH_ROOTS`, но каталога хранилищ
  с device ID, доступностью и политикой чтения пока нет.
- **Шифрование:** данные и сессии лежат на нешифрованном ext4 (см. SECURITY).
  Нужен зашифрованный каталог данных или LUKS и проверка его статуса при старте.
- **Резервные копии:** не охватывают raw, дневник, документы Ани, work style и секреты.
  Нужен явный backup manifest, отдельная политика секретов и проверяемый restore
  в новый каталог. Успех 7-Zip не доказывает полноту восстановления всего помощника.
- **Зависимости:** aiohttp используется напрямую, но не закреплён явно;
  отсутствуют package metadata, CI и матрица поддерживаемых сред. При упаковке
  нужно отвязать MCP-конфиг от интерпретатора и `PYTHONPATH` checkout.
- **Настройки при импорте:** config читает .env и создаёт константы рано; load
  дополнительно создаёт зоны и меняет права `secrets`. Нужна явная сборка зависимостей,
  удобная для тестового и production-процессов.
- **Наблюдаемость:** Health и Supervisor in-memory, некоторые проблемы не очищаются
  автоматически при восстановлении; stderr desktop не ротируется. Нужны
  согласованные состояния здоровья и ограничение размера всех журналов.
- **Управление процессами:** lock ядра относится к DATA_DIR, а lock desktop, канал Qt,
  D-Bus-имя `org.ubermensch.Anya` и скрипт KWin — общие в сеансе. Несколько стендов требуют явных идентификаторов экземпляра.

- **Обучение:** «уроки», дневник и навыки — обучение в контексте (файлы в промпте), а не
  дообучение модели. Качество уроков зависит от рефлексии; явной метрики «стало лучше» нет.
  Поручения не прерываются на полпути при сообщении пользователя: чат ждёт только замка памяти.

## Границы защиты, которые нельзя считать доказанными

bash имеет права процесса, а фильтр опасных команд эвристический. Чтение
файлов не ограничено отдельным allowlist. Снимок проверяется по активному окну,
но может содержать другое видимое чувствительное содержимое. Маркер календаря
редактируемый. Prompt `<data>` помогает модели отделять источники от инструкций,
но сам не является барьером исполнения. Подробности — в [SECURITY](SECURITY.md).

Для нового устройства сначала определить разрешённые возможности, затем выдавать
их исполнителю. Перенос той же неограниченной shell-функции на удалённый
компьютер без модели доверия увеличит последствия ошибки модели.

## Рекомендуемая последовательность

1. Усилить контракты текущего ядра: request models, локальная валидация ответа ИИ,
   согласованные таймауты и понятный результат ошибки.
2. Ввести сохраняемые runs, tool calls, approvals и delivery outbox с миграциями.
   Сначала обеспечить восстановление на одном устройстве.
3. Выделить integration/execution context вместо внутренних HTTP-callbacks
   возможностей в собственное ядро; унифицировать интерфейс провайдеров.
4. Сделать конфигурируемый реестр хранилищ и полный план резервирования существующих
   данных, включая папку Ани и дневник пользователя.
5. Добавить идентификацию и права устройств, затем второй клиент и исполнителя.
6. Выносить фоновые workers только после lease/idempotency и измерения нагрузки.

Этапы пакетов и направление границ подробнее изложены в [EVOLUTION](EVOLUTION.md).
Эта последовательность позволяет сохранять работающий desktop/Telegram и
постепенно расширять систему, не переписывая всё приложение одновременно.
