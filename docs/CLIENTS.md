# Desktop, Telegram и метрики

## Общее правило клиентов

Пользовательские интерфейсы отображают состояние ядра и отправляют команды.
Qt не открывает SQLite, не вызывает модель самостоятельно и не хранит независимую
копию задач. Telegram-бот находится в процессе ядра и обращается к Core/Store;
пользовательские Telegram-аккаунты Telethon относятся к интеграциям, а не к UI-боту.

## Desktop: три процесса

[`desktop/__main__.py`](../ubermensch/desktop/__main__.py) — supervisor, запускающий:

| Процесс | Что содержит |
|---|---|
| `ubermensch.desktop.mascot_app` | Маскот, пузыри, запрос, история, трей и связанные окна |
| `ubermensch.desktop.sheet_app` | Отдельный лист задач |

Каждый child получает свой Qt event loop и API-клиент. Падение окна не должно
завершать ядро или второй child. Supervisor использует `sys.executable`, запускает
детей с `QT_QPA_PLATFORM=xcb` (через XWayland: на Wayland окно не может само выбрать
место, а маскот ходит по экрану) и проверяет их примерно раз в секунду.

Активное окно и простой окна получают от ядра по D-Bus (`system/session.py`):
маскот прячется от чужого полноэкранного окна, а слоем листа задач управляет
скрипт KWin — лист живёт под окнами (`keepBelow`) и поднимается, когда активен
рабочий стол или сам лист. Скрипт узнаёт лист по заголовку окна `anya.exe — задачи`.
Без запущенного ядра окна работают, но этих реакций нет.

Повторный desktop supervisor блокируется `flock` файла
`$XDG_RUNTIME_DIR/ubermensch-desktop.lock`.
Сами окна используют локальные серверы для обнаружения существующего экземпляра.
Код выхода `ALREADY_RUNNING=3` приводит к ожиданию 30 секунд. После аварии задержки
2, 5, 15, 60 секунд; после 300 секунд жизни счётчик серии сбоев сбрасывается.
Штатный выход маскота с кодом 0 закрывает оба child; штатное завершение листа
приводит к его повторному запуску. Ядро при выходе desktop продолжает работать.

`desktop.log` ротируется по 2 MB с тремя резервными файлами.
`desktop-stderr.log` открывается на дописывание без аналогичной ротации. Если папка
данных недоступна, supervisor может работать без файлового лога.

Анимации и бытовое поведение маскота не требуют сетевого ИИ на каждом тике.
Изменение мордочки/движения обычно локально для UI, изменение содержимого памяти
должно проходить Core. Не помещать долгий синхронный I/O в Qt slot.

## HTTP и сигналы Qt

`Api(QObject)` использует `QNetworkAccessManager`, callbacks и Qt-сигналы:

- `state_changed(dict)` — новый снимок состояния;
- `event(dict)` — отдельное SSE-событие;
- `online_changed(bool)` — доступность потока ядра.

Основные методы: `chat`, `onboard`, `add_task`, `set_task`, `decide`, `metrics`,
`refresh`. Токен читается с диска при создании каждого запроса. База URL вычисляется
при создании Api из config; смена порта требует пересоздания клиента/процесса.

`changed` и `thinking` запускают debounce 120 ms перед запросом state. Получение
первого корректного SSE-пакета переводит клиента online и тоже вызывает refresh.
Пакеты собираются в байтовом буфере до двойного LF. Комментарии ping не становятся
пользовательскими событиями. После обрыва переподключение через 3 секунды.

Таймауты: обычный запрос 15 секунд; chat/onboard 330 секунд; SSE transfer 40 секунд
при серверном ping каждые 15 секунд. Ошибка сети без JSON error преобразуется в
сообщение «ядро недоступно». Для диагностики различать реальную потерю ядра и
таймаут долгой операции: подтверждение на сервере может ждать 600 секунд.

При добавлении поля UI сначала изменить контракт/снимок Core, затем обработчик
клиента. Новое событие может быть сигналом перечитать данные; полагаться на него
как на единственный источник долговременного состояния нельзя.

## Локальная связь окон

`QLocalServer`/`QLocalSocket` с UserAccessOption используют имена
`ubermensch-mascot` и `ubermensch-sheet`. Команды включают `show`, `prompt`,
`history`, `plan`, `metrics`; обработчик целевого процесса решает, какое окно открыть.
Ожидания соединения/записи короткие, порядка 500 ms; проверка наличия — 300 ms.

Это механизм IPC одного пользовательского сеанса (Unix-сокеты Qt). Он не является API
телефона и не заменяет HTTP Core. Имена общие для профиля: два checkout не дают
автоматически два независимых набора окон, даже если их DATA_DIR различаются.

## Telegram-бот

[`bot.py`](../ubermensch/bot.py) использует aiogram polling. Сообщения фильтруются
по `message.chat.id == TG_CHAT_ID`, callback-кнопки — по `from_user.id == TG_CHAT_ID`.
Это предполагает личный чат владельца; установка group chat ID не даёт готовый
групповой сценарий подтверждений.

| Команда | Действие |
|---|---|
| `/start` | Знакомство/приветствие |
| `/tasks` | Текущие задачи |
| `/goals` | Активные цели |
| `/memory` | Факты с ID |
| `/forget N` | Мягко скрыть факт |
| `/reminders` | Ожидающие напоминания |
| `/cancel N` | Отменить напоминание |
| `/status` | Сводка состояния |
| `/login`, `/login work` | Начать вход в пользовательский аккаунт |
| `/login_cancel` | Сбросить текущий сценарий входа |

Во время входа сообщения интерпретируются как номер/код/пароль, а не обычный чат.
Код и пароль бот пытается удалить из диалога; это не гарантирует удаления копий
из инфраструктуры Telegram. Состояние входа хранится в Core и теряется при рестарте.

Обычные сообщения направляются в общий `Assistant.handle` с каналом tg. Lock чата
общий с desktop, история общая. Ответ разбивается на части до 4 000 символов;
простая разметка преобразуется в HTML с экранированием, при ошибке отправки HTML
есть текстовый вариант. Набор/паузы имитируются средствами бота и не означают
streaming токенов модели.

`forward_events` получает reminder, notify и approval из Bus. Approvals превращаются
в кнопки решения с деталями. Ошибка отправки логируется; устойчивой очереди повторной
доставки нет. Say относится к desktop и не рассылается ботом как обычный notify.

## Метрики: контракт и интерпретация

[`metrics.py`](../ubermensch/metrics.py) считает показатели по БД без вызова ИИ.
ИИ участвует раньше — в классификации программ/страниц. `/api/metrics` возвращает
`learning` и `activity`.

### `learning`

| Поле | Содержание |
|---|---|
| `mastery` | Округлённый процент по формуле ниже |
| `jobs` | done, total, by_source: список `{label, done, total}` |
| `analyzed_chars` | Сумма chars завершённых done jobs |
| `areas` | Список `{area: русская подпись, facts, full: 60}` |
| `facts`, `people`, `goals` | Счётчики актуальных сущностей |
| `facts_by_day` | Массив 14 чисел, от 13 дней назад к сегодня |
| `events` | Список `{label, count}` по источникам |
| `dossier_at` | Курсор последнего досье |
| `voice_at`, `style_at` | mtime persona и личного стиля или null |
| `openai` | При подключённом helper: spent, budget, model; может быть null |

`mastery = round(100 × (0.6 × plan + 0.4 × coverage))`, где plan — доля
done/skipped jobs, coverage — средняя заполненность семи сфер, насыщаемая на
60 фактах на сферу. Это индикатор объёма обработки, а не измерение истинности
знаний или глубины понимания человека. Failed jobs не считаются выполненными.
`facts_by_day` считает созданные записи, включая позже скрытые; не путать его
с изменением числа активных фактов за день.

### `activity`

| Поле | Содержание |
|---|---|
| `today` | Локальная дата YYYY-MM-DD |
| `days` | 7 записей `{date, minutes, first, last, kinds}` |
| `hours` | 24 значения минут за сегодня по часам |
| `top_today`, `top_week` | До 6/8 записей `{key, minutes, category}` |
| `tasks` | open, overdue, done_today, done_week, streak |
| `goals` | `{title, done, total}` по активным целям |
| `since` | Дата первой найденной сессии **в выбранном недельном окне**, либо null |

Kinds: useful, neutral, distracting, unknown. Категории учёба/работа/музыка/развитие
считаются useful, общение/быт/система — neutral, развлечения — distracting.
Неизвестная программа не становится автоматически развлечением.

Сессии распределяются по часам, значения округляются до минут. Заголовки браузера
разбираются эвристически; для смешанных сайтов может классифицироваться отдельная
страница, а в топе они объединяются. First/last — время компьютерной активности,
не время сна или пробуждения человека. Streak — дни с завершёнными задачами;
сегодняшний ещё пустой день не прерывает вчерашнюю серию до конца суток.

## Проверка UI-изменений

Для контрактов использовать искусственный Core/HTTP-сервер. Визуально проверять
пустое состояние, длинный текст, отключённое ядро, восстановление SSE, отказ от
подтверждения и повторное нажатие. Автоматических Qt screenshot-тестов в текущем
наборе нет. Запуск реального UI подключается к адресу из config и может показывать
личные данные, поэтому демонстрационный стенд должен иметь отдельное окружение.
