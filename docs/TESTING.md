# Проверки, диагностика и передача изменений

## Базовая проверка checkout

Команды выполняются из корня проекта в bash после установки requirements:

```bash
.venv/bin/python -m unittest discover -s tests -v
.venv/bin/python -m compileall -q ubermensch tests
git diff --check
```

На момент сверки документации в [`tests/test_tool_runtime.py`](../tests/test_tool_runtime.py)
**21 тест** и в [`tests/test_profiling.py`](../tests/test_profiling.py) — **4** (окна профиля,
проверка опор и цитат, метрики, полное построение с подставным мозгом и повтор из кеша). Используется стандартный unittest, включая `IsolatedAsyncioTestCase`.
Специальных команд pytest, CI workflow и настроенного обязательного линтера в
репозитории пока нет. `compileall` проверяет синтаксис и создаёт обычный
`__pycache__`, но не подтверждает правильность выполнения программы.

Тесты не запускают полный `__main__`: они создают SQLite `:memory:`, временные
файлы и локальный aiohttp TestServer, подменяют ответы провайдеров и отправку
Telegram. Они не требуют оплачиваемого вызова ИИ и не отправляют реальные сообщения.
Чтение `.env` при импорте config возможно, но реальные provider requests в проверяемых
сценариях заменены. Не вставлять ключи в тестовые fixtures.

## Что проверено существующим набором

| Группа | Количество | Проверки |
|---|---:|---|
| `OpenAIToolTests` | 7 | Результат функции возвращается модели; usage каждого хода учитывается; неверное имя/аргументы не исполняются; фон без tools; бюджет до эффекта; предел раундов; остановка при неопределённом результате; верхняя форма финального JSON |
| `RouterTests` | 6 | Лимит до инструмента → fallback; начатый инструмент запрещает повтор; ожидание остановки primary; внешняя отмена; гонка dispatch при отмене; ожидание approval подавляет watchdog |
| `ToolAPITests` | 7 | Авторизация и единый каталог MCP/HTTP; чтение временного файла и журнал; отказ Telegram; MCP через общий API; аргументы/UUID до dispatch; 500 после эффекта; полный fallback-сценарий |
| `FallbackOutcomeTests` | 1 | Резервный ответ применяет структурированное напоминание |

Полный сценарий в `ToolAPITests` моделирует лимит Claude → OpenAI function call →
реальный локальный HTTP → чтение временного файла → результат модели → задача
и напоминание в искусственной БД. Это проверка связности контуров, не качества
ответов настоящего ИИ и не доступности конкретной облачной модели.

Для отдельного класса/метода можно использовать unittest filter:

```bash
.venv/bin/python -m unittest discover -s tests -v -k RouterTests
```

## Чего эти тесты не доказывают

- Совместимость установленной версии Claude CLI с каждым параметром запуска.
- Доступность выбранных OpenAI model IDs и все варианты ответа реального провайдера.
- Корректность эффектов KWin/D-Bus/Wayland, bash, Office-файлов и календаря.
  Сенсоры сеанса проверяются вручную внутри Plasma: `windows.foreground()` и
  `windows.idle_seconds()` из второго процесса при запущенном ядре.
- Доставку Telegram/Gmail, работу OAuth, вход в личный кабинет и сбор Chrome.
- Визуальное поведение Qt, DPI, положение окон и все сценарии завершения процессов.
- Восстановление реального архива, миграцию исторической production-базы и работу
  после внезапного выключения компьютера.
- Полноту политики безопасности, отсутствие prompt injection или обходимости
  эвристики опасных команд.

Не называть mocked integration test испытанием с реальным аккаунтом. В описании
изменения перечислять только фактически выполненные проверки.

## Подбор проверки по изменению

| Изменение | Минимально полезная проверка |
|---|---|
| Общий инструмент | Схема, неизвестные/лишние аргументы, отказ до эффекта, исполнение через HTTP; для мутации — сбой после эффекта |
| Fallback/router | Отмена, гонка dispatch, ожидание approval, запрет повторного выполнения |
| Provider loop | Несколько ходов, результат tool, usage каждого хода, предел раундов, некорректный final |
| SQL-миграция | Upgrade искусственной БД предыдущей версии, сохранность данных, повторное открытие |
| Сборщик/парсер | Маленький искусственный экспорт, пустые/битые записи, стабильные external_id, повторный сбор |
| API | Настоящий TestServer, auth, типы/статусы, snapshot/SSE при изменении |
| UI | Пустой/длинный ответ, offline/online, подтверждение, несколько окон; ручная визуальная проверка |
| Документация | Ссылки, соответствие именам маршрутов/инструментов, синтаксис примеров |

Тест должен проверять наблюдаемое правило, которое можно нарушить при рефакторинге.
Для простой правки текста не нужен новый unit test, повторяющий этот же текст.

## Изолированные fixtures

Создавать Store на `:memory:` либо временном файле, закрывать connection после
проверки. Создание настоящего `Assistant(settings, ...)` пишет промпты и MCP-конфиг:
передавать временный workspace. В существующих точечных тестах используется
`Assistant.__new__` с явной установкой нужных зависимостей — это сознательная
изоляция побочных эффектов конструктора, а не предпочтительный production API.

Подменять `config.DATA_DIR`, API port/token и зависимость отправки до выполнения
инструмента. `run_id` сам по себе не направляет запись в временный каталог:
Core строит путь журнала от текущего DATA_DIR. Нельзя использовать реальный
`telegram_send`, `run_shell` или файл в реальной папке данных как удобную fixture.

Для будущих тестов миграций не импортировать `__main__` ради Store. Нужны только
`store.py` и искусственные строки. Для parser fixtures не копировать переписку
пользователя в git даже после удаления имени: идентифицирующие данные могут
содержаться в тексте, ссылках и метаданных.

## Диагностика по слоям

### Ядро недоступно

1. Проверить существование и доступность DATA_DIR/db. На новой папке ожидание
   каталога может выглядеть как ожидание разблокировки диска.
2. Проверить конкретный процесс `-m ubermensch`, его checkout и порт; не путать
   с desktop supervisor или MCP child.
3. Прочитать хвост основного лога и вызвать `/api/health` с существующим токеном.
4. Если API отвечает, а окно offline, проверить совпадение DATA_DIR/API_PORT
   процессов и поток SSE. Два процесса с разными `.env` могут смотреть в разные места.

### Резервный ИИ не выполняет действие

1. Убедиться, что запущено обновлённое ядро: повторный `start.sh` не заменяет процесс
   (`systemctl --user restart ubermensch`).
2. Проверить наличие helper и его spent/budget, проблему openai и временную блокировку.
3. Проверить `/api/tools`: нужная функция должна быть в общем каталоге.
4. Проверить ответ `/api/tools/call`, схему аргументов и ожидание approval.
5. Если появился `ToolExecutionUncertain` или InterruptedToolRun, сначала выяснить
   фактический результат на стороне интеграции. Не повторять весь запрос автоматически.

### Анализ стоит

Сопоставить `/api/investigation`, `/api/health`, дневную/ночную паузу, недавний диалог,
лимит Claude и наличие pending jobs. Collecting не означает analyzing. Pending
job не имеет состояния running; смотреть последний лог начала/завершения и время
паузы worker. Удаление очереди/курсоров не является штатной первой диагностикой.

### Окно упало

Проверить `desktop.log` и `desktop-stderr.log`. Сбой одного child может скрываться
за его автоматическим перезапуском. Если exit code 3, другой экземпляр окна ещё
держит локальное имя. Если API жив, сначала исследовать Qt-процесс, не перезапускать
все фоновые службы вместе с ним.

### Ошибка после обновления схемы

Сохранить диагностическую копию согласованным SQLite backup и проверить
`PRAGMA user_version` на копии. Не менять production user_version вручную и
не удалять БД, чтобы «миграции пошли заново». Воспроизвести переход на fixture;
исправление оформлять следующей миграцией.

## Работа с журналами

Читать ограниченный фрагмент лога, а не публиковать его целиком. Главный лог может
содержать пути, названия документов, ошибки интеграций и часть текста ответа.
Перед передачей в issue убрать секреты и личные данные. `tools.jsonl` минимален,
но имя инструмента и последовательность всё равно раскрывают характер действий.

Не включать DEBUG-логирование HTTP Authorization, `.env`, provider body и полных
личных контекстов ради диагностики. Для воспроизведения лучше собрать искусственный
запрос с той же структурой и размером.

## Формат передачи результата разработчику

Описать поведение до/после, изменённые границы и нужный перезапуск. Указать
выполненные тесты, необходимость миграции/новой настройки и ограничения проверки.
Если изменён API/инструмент, обновить его контракт; если меняется повторяемость
или доступ к данным — SECURITY и LIMITATIONS. Обновление документации не является
доказательством применения кода в уже работающем фоновом процессе.
